## ✍️ Правила создания документации

### 1. Формат комментариев

#### В коде (Rust, TypeScript, Python)
```rust
// NEI-20251105: Краткое описание изменения (одна строка)
```

**Правила**:
- Формат: `// NEI-YYYYMMDD: описание`
- Максимум 80 символов
- Только для значимых изменений (не для опечаток/мелких правок)
- Один комментарий в начале функции/модуля

#### В документации (Markdown)
```markdown
<!-- NEI-20251105: Описание обновления документа -->
```

**Правила**:
- Формат: `<!-- NEI-YYYYMMDD: описание -->`
- Размещать в начале файла
- Можно несколько для истории изменений

### 2. Генерация CHANGELOG

**Автоматически** из всех `NEI-*` комментариев:
```bash
python tools/extract_changelog.py --output CHANGELOG.md
```

Результат — полный журнал изменений с группировкой по типам (feature, refactor, fix, docs).

## 🗂️ Типы документов

### Architecture (архитектура)
**Когда создавать**: При принятии важного архитектурного решения.

**Шаблон**:
```markdown
# Название решения

**Дата**: 2025-11-05
**Статус**: Принято | В обсуждении | Устарело

## Контекст
Описание проблемы или необходимости решения.

## Решение
Что было решено.

## Последствия
Плюсы и минусы решения.

## Альтернативы
Какие варианты рассматривались.
```

**Примеры**: `desktop-mobile-ui.md`, `p2p-collaboration.md`

### Guides (руководства)
**Когда создавать**: При добавлении новой фичи, требующей документации для пользователей.

**Шаблон**:
```markdown
# Название фичи

**Аудитория**: Разработчики | Пользователи | Администраторы

## Быстрый старт
Минимальный пример использования.

## Подробное описание
Детальная документация.

## Примеры
Реальные use cases.

## FAQ
Часто задаваемые вопросы.

## Troubleshooting
Решение проблем.
```

**Примеры**: `websocket-events-guide.md`, `quick-start.md`

### API (спецификации)
**Когда создавать**: При добавлении/изменении API endpoints.

**Шаблон**:
```markdown
# API v1 Endpoints

## Endpoint: POST /api/v1/example

**Описание**: Краткое описание.

**Request**:
```json
{
  "field": "value"
}
```

**Response** (200 OK):
```json
{
  "status": "success",
  "data": {...}
}
```

**Ошибки**:
- 400: Невалидный запрос
- 500: Внутренняя ошибка
```

## 🔄 Обновление документации

### При изменении API
1. **Обновить** `docs/api/endpoints-v1.md` (или создать)
2. **Добавить** комментарий `// NEI-YYYYMMDD: описание` в код
3. **Обновить** соответствующий guide (если есть)
4. **Запустить** `python tools/extract_changelog.py`

### При изменении ENV
1. **Обновить** `.env.example`
2. **Добавить** описание в `spinal_cord/ENV.md`
3. **Обновить** `PROJECT_HANDOVER.md` (раздел "Конфигурация")
4. **Добавить** комментарий в код

### При рефакторинге
1. **Упростить** комментарии (минимализм)
2. **Удалить** устаревшие `neira:meta` блоки
3. **Обновить** ADR в `DECISIONS.md` (если касается архитектуры)
4. **Переместить** устаревшие документы в `docs/archive/`

## 🧹 Очистка документации

### Регулярные задачи (раз в месяц)

#### 1. Архивирование устаревших документов
```bash
# Переместить в archive
Move-Item -Path "СТАРЫЙ_ФАЙЛ.md" -Destination "docs/archive/"

# Обновить README с новыми ссылками
```

#### 2. Минимизация комментариев
```bash
# Для всех .rs файлов (по одному)
python tools/minimize_comments.py --path spinal_cord/src/main.rs
```

#### 3. Генерация CHANGELOG
```bash
# Обновить журнал изменений
python tools/extract_changelog.py --output CHANGELOG.md
```

#### 4. Проверка ссылок
```bash
# Найти мёртвые ссылки в .md файлах
rg "\[.*\]\(.*\)" --type md | grep -v "http" | grep -v "^#"
```

## 📊 Метрики качества документации

### Хорошая документация:
- ✅ **Актуальная**: обновлена в течение последних 3 месяцев
- ✅ **Полная**: все endpoints/ENV/API задокументированы
- ✅ **Примеры**: есть рабочие примеры кода
- ✅ **Troubleshooting**: есть раздел решения проблем
- ✅ **Читаемая**: структура понятна новичку

### Плохая документация:
- ❌ Устарела >6 месяцев назад
- ❌ Несколько версий одного и того же (неархивированные дубликаты)
- ❌ Нет примеров использования
- ❌ Только техническое описание без контекста

## 🛠️ Инструменты

### extract_changelog.py
**Назначение**: Генерация CHANGELOG из всех `NEI-*` комментариев.

**Использование**:
```bash
python tools/extract_changelog.py --output CHANGELOG.md
python tools/extract_changelog.py --format json --output changes.json
```

**Результат**: Markdown или JSON с группировкой по типам изменений.

### minimize_comments.py
**Назначение**: Упрощение verbose `neira:meta` блоков.

**Использование**:
```bash
# Тест (без записи)
python tools/minimize_comments.py --path spinal_cord/src/main.rs --dry-run

# Реальное применение
python tools/minimize_comments.py --path spinal_cord/src/main.rs
```

**Результат**: Замена многострочных блоков на компактный формат.

## ❓ FAQ

### Q: Когда добавлять NEI-комментарий?
**A**: Для всех feature, refactor, fix изменений. Не нужно для мелких правок (опечатки, форматирование).

### Q: Как часто обновлять CHANGELOG?
**A**: При каждом значимом PR или раз в неделю (автоматически через скрипт).

### Q: Что делать с устаревшими документами?
**A**: Переместить в `docs/archive/` и обновить ссылки в README.

### Q: Нужно ли документировать каждый endpoint?
**A**: Да, минимум краткое описание + example request/response.
